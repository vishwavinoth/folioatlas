    14→# 1. EXECUTIVE SUMMARY
    15→
    16→## 1.1 Product vision
    17→
    18→Build **FolioAtlas**, a polished, searchable, SEO-optimized public directory of developer portfolios sourced from the open-source GitHub repository `emmabostian/developer-portfolios`.
    19→
    20→The website should help developers, recruiters, students, hiring managers, and engineering communities discover real developer portfolios through a fast, elegant, and accessible browsing experience.
    21→
    22→The experience should combine:
    23→
    24→- Apple's Liquid Glass-inspired visual language.
    25→- Premium, restrained macOS/iOS-inspired UI and interaction design.
    26→- Reliable, automated portfolio data synchronization from GitHub.
    27→- Server-rendered pages designed for search engine discovery.
    28→- Powerful search, filters, sorting, and browsing.
    29→- A production-ready architecture that can grow without unnecessary complexity.
    30→
    31→This is not a portfolio builder, a social network, or an arbitrary collection of invented profiles. It is a directory whose content is grounded in the upstream repository.
    32→
    33→## 1.2 Product promise
    34→
    35→**One beautiful place to discover real developer portfolios.**
    36→
    37→Visitors should be able to open the site, search for a name or technology, filter the results, inspect a portfolio entry, and visit the original portfolio in a few interactions.
    38→
    39→## 1.3 Non-negotiable requirements
    40→
    41→1. The upstream GitHub repository is the canonical source of portfolio entries.
    42→2. Do not fabricate portfolio owners, portfolio URLs, skills, employers, biographies, or project descriptions.
    43→3. Follow the supplied Apple design documentation as the primary design authority.
    44→4. Use Liquid Glass-inspired effects primarily for navigation and interactive controls, not as a blanket background for every content card.
    45→5. Deliver working functionality, not a static mockup.
    46→6. Build real SEO pages with server-rendered content and correct metadata.
    47→7. Include loading, empty, error, offline/stale-data, and accessibility states.
    48→8. Implement tests, production checks, deployment documentation, and a repeatable release process.
    49→9. GitHub authentication may be configured if necessary, but must be optional for public-repository reads and must never expose credentials.
    50→10. The MVP must be usable without an account, database, payment system, or mandatory third-party analytics service.

    54→# 2. PRODUCT GOALS AND SUCCESS CRITERIA
    55→
    56→## 2.1 Primary goals
    57→
    58→- Make the upstream portfolio list significantly easier to explore.
    59→- Make real portfolio entries discoverable through search engines.
    60→- Provide a premium and recognizable interface inspired by Apple's design principles.
    61→- Keep portfolio data synchronized with the source repository.
    62→- Deliver a maintainable, secure, fast, accessible production website.
    63→
    64→## 2.2 Success criteria
    65→
    66→The release is considered successful when:
    67→
    68→- Every valid, supported portfolio entry discovered in the upstream README is represented in the generated directory index.
    69→- Invalid, duplicate, or ambiguous records are reported rather than silently converted into fabricated data.
    70→- Search, filters, sorting, pagination, and direct URLs work.
    71→- All public pages have appropriate metadata and canonical URLs.
    72→- The production build succeeds without TypeScript errors or lint failures.
    73→- Automated tests cover parsing, filtering, sorting, synchronization, and critical user journeys.
    74→- The site passes keyboard navigation and reduced-motion checks.
    75→- No private credentials, access tokens, or unnecessary personal data are shipped to the browser.
    76→- The deployed website is functional on desktop, tablet, and mobile.
    77→- The deployment and synchronization procedures are documented.
    78→
    79→## 2.3 Explicit non-goals for the MVP
    80→
    81→Do not implement unless necessary for the core product:
    82→
    83→- User accounts or social authentication.
    84→- Developer registration and portfolio submission forms.
    85→- A database-backed profile editor.
    86→- Ratings, reviews, likes, comments, or follower systems.
    87→- AI-generated bios, skills, summaries, or recommendations.
    88→- Scraping the content of every linked portfolio website.
    89→- A paid subscription system.
    90→- A complex administrative dashboard.
    91→- A separate backend service where Next.js server capabilities are sufficient.
    92→
    93→The architecture may support future additions, but the initial release should remain lean.

    97→# 3. TARGET USERS AND USER JOURNEYS
    98→
    99→## 3.1 Audience
   100→
   101→**Developers:** Discover portfolio examples, presentation approaches, and other developers working with similar technologies.
   102→
   103→**Recruiters and hiring managers:** Explore publicly available developer portfolios and follow links to original websites.
   104→
   105→**Students and early-career developers:** Learn how other developers present their work.
   106→
   107→**Open-source contributors:** Explore entries in the upstream repository and discover the original source of the directory data.
   108→
   109→## 3.2 Core user journeys
   110→
   111→### Journey A — Discover a portfolio
   112→
   113→1. Visitor opens the homepage.
   114→2. Visitor sees the product introduction and directory search.
   115→3. Visitor enters a developer name or technology.
   116→4. Matching results appear.
   117→5. Visitor opens a portfolio entry or visits its external website.
   118→
   119→### Journey B — Explore a technology
   120→
   121→1. Visitor opens a technology directory page.
   122→2. The page explains the category and displays matching entries.
   123→3. Visitor sorts or filters the results.
   124→4. Visitor opens a portfolio.
   125→
   126→### Journey C — Browse alphabetically
   127→
   128→1. Visitor selects a letter.
   129→2. The directory navigates to the relevant alphabetical page.
   130→3. Visitor browses the available entries.
   131→4. Visitor opens the original portfolio.
   132→
   133→### Journey D — Arrive from a search engine
   134→
   135→1. Visitor searches for a developer portfolio directory or relevant technology.
   136→2. Search engine displays an eligible indexable page.
   137→3. Visitor lands directly on a meaningful page.
   138→4. Visitor can immediately browse or continue searching.
   139→
   140→### Journey E — Handle unavailable upstream data
   141→
   142→1. The source repository or GitHub API is temporarily unavailable.
   143→2. The website continues serving the last successfully generated index.
   144→3. Visitors can still search and browse existing data.
   145→4. The system records the synchronization failure and retries later.

   196→# 5. APPLE LIQUID GLASS DESIGN REQUIREMENTS
   197→
   198→## 5.1 Authoritative references
   199→
   200→The agent must study and use the following documents before implementing the UI:
   201→
   202→1. Apple Liquid Glass technology overview:
   203→   https://developer.apple.com/documentation/technologyoverviews/liquid-glass
   204→
   205→2. Apple Human Interface Guidelines — Materials:
   206→   https://developer.apple.com/design/human-interface-guidelines/materials
   207→
   208→3. Apple guidance on adopting Liquid Glass:
   209→   https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass
   210→
   211→4. Apple Human Interface Guidelines:
   212→   https://developer.apple.com/design/human-interface-guidelines
   213→
   214→The supplied materials and Liquid Glass documentation take priority over generic glassmorphism tutorials, arbitrary design trends, or an agent's default component styling.
   215→
   216→## 5.2 Translation to the web
   217→
   218→This is a web application, not a native SwiftUI application. Implement the visual language with appropriate web technologies such as CSS translucency, backdrop filters, layered highlights, controlled shadows, and fluid motion.
   219→
   220→Do not claim that CSS `backdrop-filter` is Apple's native Liquid Glass implementation.
   221→
   222→Do not add native iOS-specific APIs to a web project merely to imitate the appearance.
   223→
   224→The objective is to translate the design principles into a credible, polished web experience.
   225→
   226→## 5.3 Core design principles
   227→
   228→### A. Distinct functional and content layers
   229→
   230→The interface must clearly distinguish navigation and controls from the content being explored.
   231→
   232→**Functional layer:**
   233→- Floating primary navigation.
   234→- Search controls.
   235→- Filter controls.
   236→- Sort controls.
   237→- Popovers and menus.
   238→- Selected interactive states.
   239→
   240→**Content layer:**
   241→- Developer names.
   242→- Portfolio URLs.
   243→- Descriptions.
   244→- Technology labels.
   245→- Directory results.
   246→- Editorial text and documentation.
   247→
   248→Use Liquid Glass-inspired styling primarily for the functional layer. Keep content cards and reading surfaces comparatively restrained.
   249→
   250→### B. Glass should reveal content, not compete with it
   251→
   252→- Underlying content should remain perceptible through translucent functional elements where appropriate.
   253→- Use translucency intentionally.
   254→- Keep the visual hierarchy understandable.
   255→- Avoid stacking multiple blurred surfaces over one another.
   256→- Do not use heavy glass effects on every card, section, badge, and footer element.
   257→
   258→### C. Regular and clear variants
   259→
   260→Treat the two variants as different functional choices, not interchangeable decorations.
   261→
   262→**Regular-inspired glass:**
   263→- Default for the primary navigation and text-heavy control surfaces.
   264→- Stronger background attenuation where necessary.
   265→- Prioritize readability and separation.
   266→
   267→**Clear-inspired glass:**
   268→- Reserved for controls that genuinely sit over a visually rich background.
   269→- Use only where the background contributes meaningfully to the experience.
   270→- Apply additional contrast protection when necessary.
   271→
   272→Do not make the entire website a transparent, heavily blurred surface.
   273→
   274→### D. Contrast and adaptation
   275→
   276→- Text must remain readable over light and dark backgrounds.
   277→- Use explicit foreground colors and background fallbacks.
   278→- Do not depend on blur alone for contrast.
   279→- Respect browser and operating-system preferences where practical.
   280→- Provide a usable interface when backdrop filtering is unsupported or disabled.
   281→- Support increased contrast and reduced transparency through appropriate styles.
   282→
   283→### E. Fluidity and motion
   284→
   285→Interactions should feel lightweight and responsive.
   286→
   287→Use motion for:
   288→- Navigation state changes.
   289→- Popover presentation.
   290→- Filter activation.
   291→- Search suggestions.
   292→- Button feedback.
   293→- Subtle transitions between interface states.
   294→
   295→Avoid:
   296→- Excessive parallax.
   297→- Constantly moving backgrounds.
   298→- Heavy spring animations on every element.
   299→- Large animated blur surfaces.
   300→- Motion that delays access to the directory.
   301→- Decorative movement that distracts from search results.
   302→
   303→All nonessential motion must respect `prefers-reduced-motion`.
   304→
   305→## 5.4 Proposed visual direction
   306→
   307→Use these as initial design tokens, not official Apple specifications. Validate the values in actual browser renders and refine them to meet the design principles above.
   308→
   309→### Color foundation
   310→
   311→| Token | Starting value | Use |
   312→|---|---|---|
   313→| `--page-bg` | `#F5F5F7` | Light page background |
   314→| `--page-bg-dark` | `#101114` | Dark page background |
   315→| `--text-primary` | `#1D1D1F` | Primary light-mode text |
   316→| `--text-primary-dark` | `#F5F5F7` | Primary dark-mode text |
   317→| `--text-secondary` | `#6E6E73` | Supporting text |
   318→| `--accent` | `#0A84FF` | Restrained interactive accent |
   319→| `--border-subtle` | Low-opacity neutral | Separators and boundaries |
   320→| `--glass-surface` | Adaptive translucent neutral | Functional glass surfaces |
   321→
   322→The final palette must be contrast-tested. Never assume a color works because it resembles an Apple interface.
   323→
   324→### Material tokens
   325→
   326→Define reusable CSS variables for:
   327→
   328→- Regular-inspired glass surface.
   329→- Clear-inspired glass surface.
   330→- Material border.
   331→- Specular highlight.
   332→- Material shadow.
   333→- Backdrop blur.
   334→- Active-state highlight.
   335→- Focus ring.
   336→
   337→Possible starting values:
   338→
   339→```css
   340→:root {
   341→  --glass-regular-bg: rgba(255, 255, 255, 0.72);
   342→  --glass-regular-border: rgba(255, 255, 255, 0.65);
   343→  --glass-clear-bg: rgba(255, 255, 255, 0.38);
   344→  --glass-blur: 20px;
   345→  --glass-radius: 20px;
   346→}
   347→```
   348→
   349→These are implementation starting points only. They must be adapted for light mode, dark mode, actual backgrounds, contrast, and browser support.
   350→
   351→Do not copy these values indiscriminately to every component.
   352→
   353→### Typography
   354→
   355→- Use a clean system-first sans-serif stack.
   356→- Prefer native system fonts over downloading a large font family solely for an Apple-like appearance.
   357→- Use clear typographic hierarchy.
   358→- Keep body text comfortable to read.
   359→- Avoid excessive letter spacing, uppercase labels everywhere, and oversized headlines that push the directory below the fold.
   360→
   361→Suggested stack:
   362→
   363→```css
   364→font-family:
   365→  -apple-system,
   366→  BlinkMacSystemFont,
   367→  "Segoe UI",
   368→  sans-serif;
   369→```
   370→
   371→Do not use Apple's proprietary font files without the appropriate rights.
   372→
   373→### Shape and spacing
   374→
   375→- Use consistent radii for controls, popovers, and content containers.
   376→- Avoid giving every element a different rounded-pill shape.
   377→- Keep page gutters and content widths consistent.
   378→- Give search and filtering controls sufficient touch targets.
   379→- Use whitespace to establish hierarchy rather than relying on blur and shadows.
   380→
   381→### Iconography
   382→
   383→- Use one consistent icon library, such as Lucide.
   384→- Keep icons minimal and recognizable.
   385→- Include visible text for important actions.
   386→- Do not use emoji as the primary icon system.
   387→- Ensure decorative icons are hidden from assistive technology when appropriate.
   388→

   412→## 5.6 Portfolio card requirements
   413→
   414→Each card may display only information available from a validated source or generated classification.
   415→
   416→Required where available:
   417→- Developer name.
   418→- Original portfolio URL.
   419→- Short description, only if supplied.
   420→- Verified or transparently classified technology labels, if available.
   421→- External-link indicator.
   422→
   423→Optional:
   424→- Alphabetical index.
   425→- Source attribution.
   426→- A lightweight interaction to copy or open the URL.
   427→
   428→Do not fabricate headshots, company logos, professional biographies, ratings, profile statistics, or project previews.
   429→
   430→Do not automatically fetch every portfolio's favicon or screenshot during server rendering. This creates reliability, privacy, and security concerns. Any future preview feature must be separately designed, safe, and optional.
   431→
   432→## 5.7 Accessibility requirements
   433→
   434→- Semantic HTML.
   435→- Keyboard-operable navigation, search, filters, menus, and pagination.
   436→- Visible focus indicators.
   437→- Accessible names for icon-only buttons.
   438→- Proper heading hierarchy.
   439→- Sufficient text contrast.
   440→- No information conveyed by color alone.
   441→- Respect reduced motion.
   442→- Support zoom and narrow viewports.
   443→- Do not trap focus in nonmodal popovers.
   444→- Use modal dialog semantics only for actual modal interactions.
   445→- Test with automated accessibility tools and manual keyboard navigation.

   576→# 7. GITHUB SOURCE AND DATA PIPELINE
   577→
   578→## 7.1 Source of truth
   579→
   580→Canonical repository:
   581→
   582→`https://github.com/emmabostian/developer-portfolios`
   583→
   584→The implementation must verify the repository's actual structure before assuming the README layout. Do not invent additional data files or APIs that are not present.
   585→
   586→Default source:
   587→- Repository: `emmabostian/developer-portfolios`
   588→- Branch: determine the actual default branch through GitHub metadata.
   589→- File: `README.md`, unless inspection identifies a more authoritative maintained source.
   590→
   591→The source URL and repository attribution must be visible on the website.
   592→
   593→## 7.2 Data ingestion
   594→
   595→Implement a deterministic pipeline:
   596→
   597→1. Fetch the README from the upstream repository.
   598→2. Handle GitHub rate limits and network errors.
   599→3. Parse supported portfolio entries.
   600→4. Normalize whitespace and URLs.
   601→5. Validate required fields.
   602→6. Deduplicate entries.
   603→7. Classify entries only when classification rules are documented.
   604→8. Produce a generated data artifact.
   605→9. Produce a validation report.
   606→10. Publish the new data only after the pipeline passes validation.
   607→
   608→The parser must be tested against actual repository content, not just an invented sample.
   609→
   610→## 7.3 Suggested data schema
   611→
   612→```ts
   613→export type Portfolio = {
   614→  id: string;
   615→  name: string;
   616→  url: string;
   617→  description?: string;
   618→  technologies?: string[];
   619→  source: {
   620→    repository: string;
   621→    file: string;
   622→    line?: number;
   623→  };
   624→};
   625→```
   626→
   627→Requirements:
   628→
   629→- `id` must be deterministic across builds.
   630→- `name` must originate from the upstream entry.
   631→- `url` must be a validated HTTP or HTTPS URL.
   632→- `description` must only be included if actually present.
   633→- `technologies` must only contain supported, verified classifications.
   634→- `source` must preserve provenance.
   635→
   636→Do not use a random UUID for each build. Prefer a deterministic identifier derived from the normalized source entry or a stable source identifier.
   637→
   638→## 7.4 Parsing rules
   639→
   640→The parser must:
   641→
   642→- Recognize the actual Markdown patterns used by the repository.
   643→- Support common Markdown link forms.
   644→- Handle optional descriptions where the format permits them.
   645→- Ignore unrelated headings and prose.
   646→- Detect malformed entries.
   647→- Avoid interpreting arbitrary README text as a portfolio.
   648→- Preserve meaningful Unicode names.
   649→- Reject unsafe or unsupported URL schemes.
   650→- Handle duplicate URLs and names without silently deleting valid, distinct entries.
   651→- Report entries that require manual review.
   652→
   653→If the upstream format changes, the parser should fail visibly or produce a degraded validation report instead of publishing corrupted data.
   654→
   655→## 7.5 URL validation and normalization
   656→
   657→- Allow `https://` and, where necessary, `http://`.
   658→- Reject `javascript:`, `data:`, `file:`, and other non-web schemes.
   659→- Reject credentials embedded in URLs.
   660→- Normalize hostnames and safe URL formatting.
   661→- Do not silently remove meaningful path segments.
   662→- Do not assume every URL with the same domain is a duplicate.
   663→- Do not automatically redirect to a guessed HTTPS variant unless the original URL is verified.
   664→- Use `rel="noopener noreferrer"` for links opened in a new tab.
   665→
   666→External URLs are untrusted data. Render them as text and safe links; never execute source-provided markup.
   667→
   668→## 7.6 Duplicate handling
   669→
   670→Use multiple signals:
   671→- Exact normalized URL.
   672→- Canonical hostname and path where safe.
   673→- Stable upstream entry identity, when available.
   674→
   675→The pipeline must report collisions and apply an explicit policy. Avoid collapsing two different people into one entry simply because they share a hosting platform or domain.
   676→
   677→## 7.7 Technology classification
   678→
   679→The upstream repository may not supply structured technology metadata.
   680→
   681→If classifications are needed, implement a separate, transparent classification layer.
   682→
   683→Rules:
   684→- Only use explicitly supported evidence.
   685→- Prefer a deterministic mapping from verified source descriptions or manually reviewed classification data.
   686→- Never infer that a portfolio uses React simply because its URL contains a common hosting domain.
   687→- Do not scrape portfolio websites for technology detection in the MVP.
   688→- Keep unclassified entries in the general directory.
   689→- Explain the classification methodology on the website.
   690→- Make it possible to regenerate classifications without changing the source README.
   691→
   692→If reliable classification cannot be implemented for the available data, ship the directory with name and URL search first, and defer technology filters rather than fabricate tags.
   693→
   694→## 7.8 Generated artifact and atomic updates
   695→
   696→Generate a JSON artifact with:
   697→- Schema version.
   698→- Source repository and branch.
   699→- Source commit SHA when available.
   700→- Generation timestamp.
   701→- Valid entries.
   702→- Validation statistics.
   703→
   704→Example structure:
   705→
   706→```json
   707→{
   708→  "schemaVersion": 1,
   709→  "source": {
   710→    "repository": "emmabostian/developer-portfolios",
   711→    "file": "README.md",
   712→    "commit": "SOURCE_COMMIT_SHA"
   713→  },
   714→  "generatedAt": "ISO_TIMESTAMP",
   715→  "portfolios": []
   716→}
   717→```
   718→
   719→The example's commit and timestamp are placeholders, not real values.
   720→
   721→Write to a temporary file, validate the output, and replace the previous artifact only after success.
   722→
   723→A failed sync must not erase a previously valid production index.
   724→
   725→## 7.9 Synchronization strategy
   726→
   727→Implement:
   728→
   729→- Manual local command for developers.
   730→- Build-time generation or validation.
   731→- Scheduled synchronization using GitHub Actions.
   732→- Optional manual workflow dispatch.
   733→- Failure notifications through CI logs; add external notifications only if configured.
   734→
   735→The scheduled job should:
   736→1. Fetch upstream source.
   737→2. Run parsing and validation.
   738→3. Compare generated data with the existing artifact.
   739→4. Run relevant tests.
   740→5. Create an update pull request or commit according to the chosen repository policy.
   741→6. Avoid empty commits when no meaningful data changed.
   742→7. Preserve auditability.
   743→
   744→Prefer a pull request for source-data changes when repository governance or review requirements make it appropriate. Direct commits are acceptable only when the target repository is owned and configured for that workflow.
   745→
   746→Never require a long-lived write token simply to read a public repository.

   750→# 8. GITHUB AUTHENTICATION AND SECRETS
   751→
   752→## 8.1 Default behavior
   753→
   754→Public GitHub repository reads should work anonymously where the API or raw-content endpoint permits.
   755→
   756→If the pipeline encounters rate limits, an optional read-only token may be configured.
   757→
   758→Use the least-privileged token type and permissions supported by the selected GitHub integration. Read-only source access is sufficient for ingestion.
   759→
   760→Write permissions are only required if the chosen automation must create pull requests, push generated artifacts, or modify a repository.
   761→
   762→## 8.2 Configuration
   763→
   764→Provide a documented `.env.example`, for example:
   765→
   766→```dotenv
   767→GITHUB_TOKEN=
   768→GITHUB_OWNER=emmabostian
   769→GITHUB_REPO=developer-portfolios
   770→GITHUB_REF=
   771→GITHUB_README_PATH=README.md
   772→NEXT_PUBLIC_SITE_URL=
   773→```
   774→
   775→Requirements:
   776→- Determine the default branch when `GITHUB_REF` is not set.
   777→- Keep all server-only credentials out of `NEXT_PUBLIC_*`.
   778→- Never commit a populated `.env` file.
   779→- Never print tokens in logs.
   780→- Never include tokens in error messages or generated artifacts.
   781→- Do not place a GitHub token in browser-side requests.
   782→- Validate environment variables at startup or during build.
   783→- Document token creation, permissions, rotation, and revocation.
   784→
   785→## 8.3 Git access for the AI agent
   786→
   787→If the agent needs access to a private repository or write operations, request only the necessary authorization through the user's approved GitHub connection or credential mechanism.
   788→
   789→Do not ask the user to paste a personal access token into chat if a safer authenticated integration is available.
   790→
   791→Do not attempt to bypass repository permissions, branch protection, review requirements, or organizational policies.
   792→
   793→If authentication is unavailable:
   794→- Continue local development where possible.
   795→- Explain which repository operation is blocked.
   796→- Provide a clear, minimal setup instruction.
   797→- Do not claim a push, PR, or deployment succeeded unless verified.

   839→- Name A–Z.

   864→
   865→- Do not load the entire UI framework or large animation bundles unnecessarily.
   866→- Avoid rendering the complete directory in the browser if the source becomes large.
   867→- Use server rendering for the initial directory state.
   868→- Keep search behavior responsive on modest devices.
   869→- Add virtualization only if measurements show it is necessary.
